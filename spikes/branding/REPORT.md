# Task 0011: Craft apps, branding and window controls (read-only source research)

Method: shallow clones at each app's pinned tag (versions from `rocket-craft/src/shared/craft-apps.ts`) plus `storytold/craft-libs` HEAD, in `/tmp/brand`; `gh api` for issues. Nothing was built or run. Reproduce with `task-0011-evidence/reproduce.sh <empty dir>`. Paths below are relative to each app's repo at its tag (`<app>/…`); line numbers are at that tag.

## Short answer

1. **Nothing is shared.** Every app has its own `crates/ui-egui` with its own copy of links, start screen, title bar and logo code. `craft-libs` (only `craft-ui`: icons, buttons, tabs, layout, theme, docking) contains no Discord, ArtCraft, title-bar or window-control code, and no Cargo.toml in the 12 repos at the pinned tags depends on it. One shared patch cannot cover the 12; the patch has to be applied 12 times (a similar diff shape, different files).
2. **Window buttons: only PhotoCraft and VectorCraft draw them on Linux, and both can switch them off today** with the `systemTitleBar` preference. The other 10 never call `with_decorations(false)`, so on Linux they use the window manager's frame, which Craft Studio's overlay already strips (`_MOTIF_WM_HINTS` decorations=0, `spikes/native-dock/REPORT.md:262`). No patch needed for buttons in 10 of 12.
3. **Branding is the real problem and has no off switch in 9 of 12 apps.** Today only PhotoCraft (start screen), VectorCraft (start screen), EffectCraft (start screen on launch), and WordCraft (title-bar Discord only) have a setting that hides part of it. The "ArtCraft" text is also in every app's Help menu and About dialog, which a user can open.
4. **Recommendation:** ship launch options now for PhotoCraft (the only app in the first release), accept that Help › and About still say ArtCraft until we have our own builds, and build patched copies only for the apps where the visible default screen carries branding that settings cannot hide. Details at the end.

## Window decorations in detail (question 2)

- **PhotoCraft and VectorCraft** draw their own caption buttons on Windows and Linux (`const CUSTOM_TITLEBAR = !cfg!(target_os = "macos")`, `photocraft/apps/photocraft/src/main.rs:60`, `vectorcraft/apps/vectorcraft/src/main.rs:401`) and set `.with_decorations(!custom_titlebar)`. Both read a `systemTitleBar` preference before the window opens to go back to system decorations (`main.rs:63-69` / `main.rs:405-408`).
- **The other 10** build their viewport without `with_decorations(false)` (viewport blocks listed in the table). `with_fullsize_content_view`, `with_titlebar_shown(false)` and `with_title_shown(false)` (FilmCraft, LightCraft, DesignCraft, DeckCraft, CADCraft, WordCraft; PdfCraft only if `integrated`; GridCraft only on macOS) are macOS-only window options in winit, so on Linux the OS frame is used (the apps' own bars handle only drag and double-click-maximize, e.g. `filmcraft/crates/ui-egui/src/header.rs:19-25`, `cadcraft/crates/ui-egui/src/chrome.rs:83-87`). I did not run them to confirm the frame appears; this is read from the code, and it matches the apps' open issues ("Window decorations and title bar inconsistent with VectorCraft / PhotoCraft", e.g. designcraft #440, filmcraft #950, deckcraft #113, soundcraft #174, lightcraft #881, pdfcraft #1001, cadcraft #541, wordcraft #523), which ask for custom bars plus a `System Title Bar` preference. **When those land, each of those apps will get PhotoCraft's behaviour (own buttons, preference to turn off).**
- Docked, Craft Studio's overlay removes the WM frame (`spikes/native-dock/REPORT.md:262`), so buttons from a WM frame are not a problem. The remaining closing risk is an app's own Close (File › Exit/Quit): not a decoration issue; handled by Craft Studio.

## Shared crates (question 3)

- `craft-libs` has one crate, `craft-ui` (`craft-libs/README.md` Libraries; `crates/ui/README.md`): SVG catalogs, icon buttons, tabs, layout, theme, docking. A grep of `craft-libs/crates` for discord, artcraft, titlebar, title_bar, caption_button, decorations finds nothing. No Cargo.toml in the 12 repos at their pinned tags has a `craft-ui` dependency (`grep -rn "craft-ui =" --include=Cargo.toml`: only `craft-libs/Cargo.toml:14`).
- Each app has `crates/ui-egui` as a path crate (`<app>/Cargo.toml` `<app>-ui-egui = { path = "crates/ui-egui" }`), so the code is copied across repos, not shared. The names are consistent across apps (`links.rs`/`about`/`chrome.rs`/`header.rs`/`titlebar.rs`), which makes a scripted patch plausible, but each patch differs.
- The i18n tables also carry the strings (`designcraft/crates/ui-egui/src/i18n.rs:746,1024`, `effectcraft/crates/ui-egui/src/i18n.rs:843,1467`); hiding the widgets leaves them unused, not shown.

## Upstream (question 4)

Searched `org:storytold` issues with `gh api search/issues` on 2026-10-11:

- **Embedding of the web build:** open "Web: opt-in embedding bridge for host pages (?host=parent)" in photocraft #3101, gridcraft #237, effectcraft #698, vectorcraft #1094, cadcraft #509, wordcraft #405, deckcraft #108; photocraft #2263 "Web: an embedding API". These are for the web build, not the desktop window.
- **Embedding of the desktop UI:** merged PR #1960 (photocraft, 2026-10-10, "Panels::rail and Panels::menu_bar let an embedding app hide the icon rail and the menu bar"). This is a Rust-API flag for apps that embed PhotoCraft's egui UI, reachable from the control channel as `ui.set {panels:{menu_bar:false}}`. FilmCraft has the equivalent `show_header` (state flag only). No issue asks for a "kiosk", "no welcome" or "embedded" launch mode for the desktop apps; the nearest are branding complaints.
- **Discord promotion:** photocraft #1726 "Move the Discord promotion out of primary UI into the Help menu" (open; the maintainer decision is cited in PR #1737 "ui: remove the title-bar Discord button", open) would remove the title-bar button and the start-screen primary button, keeping Help › Join the ArtCraft Discord and the About button. Related: filmcraft #322 "Change discord ad location", vectorcraft #663, designcraft #396. If #1726/#1737 land, PhotoCraft's start screen and title bar lose Discord upstream, but "ArtCraft" in the link row and Help remains.
- **Linux window controls:** photocraft #2605 "Linux: more native looking window controls", #3185 "Linux versions need better window decorations"; artcraft #2008 "Use system title bar and borders".

No issue or PR proposes an environment variable or CLI flag to hide branding. A small upstream PR (one env var or `--embedded` guarding the sites above) is plausible given the maintainers already accepted PR #1960, but nothing exists yet, and I did not contact upstream.

## Recommendation

**Now (Phase 2, PhotoCraft only): launch options, no patching.**

1. Launch every app with its own config dir where the app supports it (`PHOTOCRAFT_CONFIG_DIR`; other apps' config location differs: VectorCraft `ui.json` per `apps/vectorcraft/src/prefs_dir.rs:1-21`, WordCraft `ui.json` under `$XDG_CONFIG_HOME/wordcraft`, which Craft Studio already needs for the control key) and pre-seed it once:
   - PhotoCraft `preferences.json`: `{"interface":{"systemTitleBar":true},"general":{"autoShowHomeScreen":false}}` (key spelling checked against `#[serde(rename_all = "camelCase")]`, `prefs.rs:277`; whole struct deserialises with defaults per `#[serde(default)]`). Result: no caption buttons, no brand mark, no start-screen Discord/ArtCraft links.
   - Then, once the control channel is up, optionally send `ui.set {"panels":{"menu_bar":false}}` only if we want to drop the title-bar Discord pill too, at the cost of losing the app's own menus. I would not: keep menus; the Discord pill is the one remaining item and PR #1737 may remove it.
2. Accept for now that Help › and About mention ArtCraft/Discord (user-initiated, and the 0.7.0 build is the upstream release, unmodified). If the rule is "ArtCraft text must never be visible" this is not enough; see below.
3. To make the empty window not look broken, have Craft Studio open a blank document or the dropped file on launch (the control server can; not tested here).

**For the apps that come next: patching our own copies is justified only where branding is on the default screen and has no setting:** FilmCraft, LightCraft, PdfCraft, DesignCraft, DeckCraft and the EffectCraft header (7 apps; roughly 8 to 20 lines each, ~100 lines in total, mechanical guard-by-env-var). VectorCraft, WordCraft and PhotoCraft can first rely on settings. SoundCraft, GridCraft and CADCraft show nothing on the main screen; leave unpatched.

**Cost of patched copies** (`docs/craft-studio-performance-plan.md:33-36,156-166`): about 6 minutes per desktop release build, measured only on PhotoCraft (not re-measured), one shared release-only target dir, 74 GB disk free and PhotoCraft's existing target dir alone is 27 GB (23 GB debug), disk budget guard at 30 GB. For 7 patched apps this is a first build of roughly 6 minutes plus the incremental ones, but the apps are separate Cargo workspaces: a shared target dir shares egui/wgpu/crate compilations only if versions, features and profile match across repos (Cargo.lock differences will recompile). I did not measure that. Also, a patched app needs our copy kept in step with every upstream release (the release tarballs we install now are verified against `SHA256SUMS`; our builds would not be).

**Better than 7 forks:** one upstream PR per app adding an `--embedded` flag (or `CRAFT_EMBEDDED=1`) that hides Discord/ArtCraft links and window buttons, using PhotoCraft's merged `menu_bar`/`rail` precedent. Then Craft Studio launches upstream releases with a flag, the build cost disappears, and the user's trademark constraint is met without forks. This needs the user's go-ahead because it is outward-facing (a PR on storytold repos); I did not do it.
